# Prepare PIG 0.3.4 for AWS

This release replaces the Python supervisor with Go and moves required HTTPS
collector ingress into the bootstrap chart. `PIGDeployment` no longer contains
an endpoint block. The source package and both charts use version 0.3.4. The
analyzer requirements remain identical to 0.3.3: controller protocol 1, schema
revision 4, and PostgreSQL 15–18. Azure and GCP remain experimental.

Source preparation permits an explicit AWS-only owner sign-off in place of
stored acceptance reports. It does not record approval of candidate artifacts or
change the stable catalog. A new acceptance record follows candidate verification.

## Artifact selection

- Public source: use the merged 0.3.4 preparation commit, containing the Go rewrite
  from PR #37 and Helm-owned collector ingress with the cloud enrollment route.
  Record the actual candidate workflow's source commit, rather than assuming `main` stayed fixed.
- Supervisor: build a new candidate from that source. Verify `--version` reports
  `0.3.4` and the OCI revision matches the accepted source commit.
- Analyzer: retain the immutable image selected by [0.3.3](../catalog/releases/0.3.3.json):
  `ghcr.io/promptless/pig-trace-analyzer@sha256:db7ba6dafc5c59fe8caa454273ced5c4deafcdc9bf82e564ae5b694ee8a0bc84`.
  Execute its `deployment-capabilities` command against
  [0.3.4 requirements](requirements/0.3.4.json) before acceptance. Keeping the same
  digest avoids introducing an analyzer change into the supervisor release.
- Acceptance: add `releases/acceptance/0.3.4.json` only after the exact source,
  supervisor digest, analyzer digest, and canonical requirements digest are known.
  No approval timestamp or evidence URL is supplied by this preparation.

After source review and merge, and with candidate publication authorized:

```sh
gh workflow run candidate.yml --repo Promptless/pig-deploy --ref main
```

## Upgrade from 0.3.3

Use the [operator ownership handoff](../UPGRADING.md) for existing installations.
This is an explicit bootstrap upgrade: remove the entire `spec.endpoint` block,
apply the target CRD, and remove all ingress permissions from the supervisor Role.
Helm does not update an existing CRD. Supply the existing hostname, class, TLS,
and annotations as chart values, and adopt the existing Ingress into Helm with
its UID preserved and its PIGDeployment owner reference removed.

Complete any active transition first and coordinate supervisors sharing the CRD.
Preserve the deployment's UID, status, and release policy. Removing endpoint
settings changes the analyzer configuration hash once, requiring revalidation;
later ingress edits do not change it. Then start the accepted Go image following
the operator procedure. A paused in-progress migration/verification is not a
completed transition and must be resolved using its original candidate first.

Record these operator interventions when evaluating the upgrade. This handoff
does not establish an unattended Python-to-Go self-update. A separate self-update
test needs a compatible starting CRD, Role, and deployment spec. Preserve the
existing [schema-3 update fixtures](../catalog/testing/aws-updates/README.md);
they do not exercise this schema-4 release or the Go replacement.

For an authorized AWS canary, record the exact artifacts and check:

- A clean installation and the 0.3.3 operator upgrade using S3, workload identity,
  and verified PostgreSQL TLS.
- Namespace Lease takeover, preserved deployment UID/status and transition state,
  and successful reconciliation by the Go process under the bootstrap Role.
- Pause/pin, blocked transition resume, credential rotation, ingress retention and
  HTTPS reachability, and recovery from interruption at a safe checkpoint.
- A fresh enrolled-host trace with its native object readable, successful analysis
  of the matching fingerprint, hosted acknowledgement, and Dashboard confirmation.

Retain existing analysis controls. If analysis remains disabled, canonical
analysis acceptance remains pending. Keep rollback declarations empty unless an
eligible recovery path has been tested and the report-backed policy permits it.

## Acceptance and publication

For the AWS-only exception, obtain the release owner's explicit approval of the
verified candidate inventory. The acceptance record must name the actual owner,
use the actual timezone-aware approval time, set `scope: "aws-only"`, and state
which checks remain unverified. Approval must be within 14 days of publication.
Omit cloud reports and keep `rollbackTo: []`. Do not claim that owner approval
proves the Python-to-Go upgrade, supervisor self-update, recovery, or canonical
analysis pipeline. The exception does not certify Azure or GCP.

Compute `requirementsDigest` from the parsed requirements model's canonical JSON
as described in [release operations](../RELEASING.md#candidate-and-acceptance).
Validate the completed record before its review and merge:

```sh
uv run --frozen pig-release evidence --version 0.3.4 \
  --evidence releases/acceptance/0.3.4.json
```

After the acceptance PR merges, authorized publication follows
[publication and promotion](../RELEASING.md#publication-and-promotion):

```sh
gh workflow run publish.yml --repo Promptless/pig-deploy --ref main -f version=0.3.4
```

Require the workflow's anonymous image/chart pulls, image execution, checksums,
and immutable artifact comparisons to pass. Review its catalog promotion PR and
coordinate the operator prerequisites above before making 0.3.4 eligible for
stable updates. Preserve the immutable manifest commit when merging promotion.
Finally verify public selection with `uv run --frozen pig-release-inspect --version 0.3.4`.
Publication and catalog selection remain separate from live installation acceptance.
